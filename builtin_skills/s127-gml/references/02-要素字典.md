# 要素字典

选型判断 + 各要素类的专有属性 + 必填项 + 几何约束 + 允许的关联。

**权威来源是 `schemas/S127.xsd`**，机器可读的版本在 `scripts/s127_schema.py`
（由 `gen_s127_schema.py` 生成）。本文档是给人看的摘要，冲突时以 XSD 为准。
S-127 共 22 个地理要素类、10 个信息要素类、2 个关联类。

> **「有则填、无则不填」**：XSD 里 `minOccurs=0` 的元素一律不强制 ——
> 原文提到就填，没提到就留空。`validate_featureset.py` 只对 XSD 必填项报 ERROR。

---

## 一、S-127 五大地理要素类型（指南第 2 章）

| # | 类别 | 内容 |
|---|---|---|
| 1 | 航线和航道 | IMO / 非 IMO 定线制、推荐航线（含渔船推荐航路） |
| 2 | VTS 及相关要素 | 船舶交通服务、报告点/线、雷达覆盖、信号站 |
| 3 | 引航要素 | 引航区、引航登离轮点、引航服务 |
| 4 | 水位信息要素 | 富余水深要素、水道区域 |
| 5 | 特定区域 | 军事演习区、安全区、船舶避险区、碰撞高风险警示区等 |

> **不表达**：无线电、雷达等通信设施的覆盖范围。

> **`controlAuthority` 只存在于 11 个要素类上**（VTSA、SRSA、RestrictedArea 两类、
> WaterwayArea、PlaceOfRefuge、UCMA、PilotService、LocalPortServiceArea、
> MilitaryPracticeArea、PiracyRiskArea）。`RouteingMeasure`、
> `ConcentrationOfShippingHazardArea`、`UnderkeelClearanceAllowanceArea`、
> `RadioCallingInPoint`、`CautionArea`、`PilotageDistrict` 等
> **schema 上根本没有这个关联**。指南 5.3「所有地理要素必须关联唯一 Authority」
> 对它们只能间接实现：`componentOf` 聚合到 VTSA/SRSA；或 `theRxN` 关联 Regulations，
> 再由 Regulations 的 `theOrganisation` 指向 Authority；或只在值班子系统内关联
> —— 生产记录表里写「Authority（系统关联）」正是这种情况。

> `ShipReport` 用 `reportTo`（→Authority）、`mustBeFiledBy`（→Applicability），
> **不是** `controlAuthority` / `permission`。
> `Authority` 用 `theContactDetails`、`theServiceHours`、`theShipReport`、`theInformation`。

## 三、选型判断表

从条文特征出发，反查该建什么要素。

| 条文特征 | 要素类 | 备注 |
|---|---|---|
| VTS 服务区、分区 | `VesselTrafficServiceArea` | 分区与总区**都要建**，关联都要完整 |
| 船舶报告制覆盖区 | `ShipReportingServiceArea` | 与 VTSA 范围相同时各自关联对应来源的 ShipReport |
| 报告线 / 报告点 | `RadioCallingInPoint` | 聚合关联到 SRSA/VTSA |
| 定线制、通航分道、深水航路、推荐航路 | `RouteingMeasure` | 见 `categoryOfRouteingMeasure` |
| 限速、单向/双向通航、禁止追越、禁止掉头、桥区范围 | `RestrictedAreaNavigational` | 有专有属性可用时优先 |
| 需经安全条件核查才可进出的监管范围 | `RestrictedAreaRegulatory` | 配 Regulations（`included`） |
| 富余水深要求 | `UnderkeelClearanceAllowanceArea` | **每个条件各建一个**，几何可相同 |
| 动态富余水深管理 | `UnderkeelClearanceManagementArea` | `dynamicResource=2/3` 时必须关联 ContactDetails |
| 港池、航道、航段、**禁止会遇**区域、桥区水域（净空高） | `WaterwayArea` | 「禁止会遇」**不建**限制区 |
| 商渔船碰撞高风险警示区 | `ConcentrationOfShippingHazardArea` | 商船 code 1 / 渔船 code 3 |
| 警戒区（追越、穿越要求与通航分道不同） | `CautionArea` | ENC 未表达时才建 |
| 船舶避险推荐水域 | `PlaceOfRefuge` | `status = recommended` |
| 引航区 | `PilotageDistrict` | |
| 引航登离轮点 | `PilotBoardingPlace` | **一般与 ENC 一致 → 不表达** |
| 引航服务覆盖范围/资质 | `PilotService` | |

### 不建地理要素的几种情况（指南 5.14）

1. **需满足特定条件**（能见度、气象、水文）才成立 → 优先建**信息要素**
   - 「潮州供水枢纽上游库区正常蓄水位期间…航速不得超过5节」
     → 不建限制区/UCAA，只建 `WaterwayArea` 并把条文填 `textContent`
   - 「能见度小于1500米时，10万载重吨以上船舶不得驶入龙腾航道」
     → 建规则信息要素，关联航道**及其所在港区/水域**（如湛江 VTS 区域），
       让船员进入港区、未抵达航道前就能拿到该信息
2. 禁止锚泊/捕捞/作业等规定 → 填进相关要素属性，**不专门为它建地理要素**
   - 渔船推荐航线的航法、航行注意事项 → 填 `RouteingMeasure` 的文本属性
3. 条文只与单一地理要素相关 → 填该要素 `textContent`，**不建信息要素**

### rxnCode（结构化分类）

把自然语言规则转成可筛选的分类：

| 子属性 | 含义 |
|---|---|

| `headline` | 把规则主体/主题概括成分类名称 |

## 五、专项编码要求

### 5.1 Applicability（指南 5.4）

- 能用 `categoryOfVessel` 表达的船舶类型，**不必**再选货物类型（客船 → `categoryOfVessel = passenger vessel`）
- `logicalConnectives`：
  - 仅用**单一**简单/复合属性描述一类船舶 → **留空**（「客船」「国内船舶」「船长大于30米的船舶」）
  - `logical conjunction`（AND）：所有条件均为真（「300总吨及以上的中国籍船舶」）
  - `logical disjunction`（OR）：满足其一即可（「船长大于50米**或**船宽大于20米的船舶」）
  - **无法同时表达 AND 与 OR** → 拆成多个 APPLIC（如「船长大于50米且吃水大于10米的货船或客船」）
- 参数无法用专用属性表达时用 `information/text`。
  即使内容与 `featureName` 相同**也仍需填** `information`
  —— 它在语义上等同于枚举值，不填就等于没界定船舶类型。
- 仅能用 `information` 表达参数的船舶类型，若描述文字已填进相关要素属性，可不再建 APPLIC。
- **总吨（Gross Tonnage）**是容量指征，单位 `gross ton`；
  **「XX吨级」**是载重量区间，文件未给具体参数时**只能用 `information` 描述**。

示例：
```jsonc
{ "ref": "applic-cn300", "type": "Applicability",
  "featureName": { "eng": "Chinese-flagged Ships of 300 Gross Tonnage and Above",
                   "zho": "300总吨及以上的中国籍船舶" },
  "attributes": {
    "logicalConnectives": "logical conjunction",
    "categoryOfVesselRegistry": "domestic",
    "vesselsMeasurements": [ { "comparisonOperator": "greater than or equal to",
                               "vesselsCharacteristics": "gross tonnage",
                               "vesselsCharacteristicsValue": 300,
                               "vesselsCharacteristicsUnit": "gross ton" } ] } }
```

### 5.2 Authority / ContactDetails / ServiceHours（指南 5.3）

- **所有地理要素必须关联唯一 Authority。**
  「由XXX机构监管」「XXX是实施本细则的主管机关」→ 该文件创建的所有地理要素都关联这个 Authority。
- ContactDetails 可**直接**与地理要素关联，表达在该范围内联系责任机构的详细信息。
- `administrativeDivision` 用于表达**省级**行政区划。
- 除无线电通信外，其他联系方式的 `categoryOfCommPref` **不填**。
- `communicationChannel`（直接属性）填机构呼叫/工作频道，如 `VHF CH16`，可多个。
- VTS 区内划分若干分区、各分区频道不同 → 用复合属性 `radiocommunications`
  （**注意 XSD 里 c 是小写**，指南正文写作 radioCommunications）：
  子属性 `communicationChannel` 填各分区频道，`contactInstructions` 填对应分区信息。
  同类联系方式按重要程度排序。
  > ⚠️ CARIS S-57 Composer **不支持** `radiocommunications`，需在值班子系统内补充编辑。
- 「XXX保持24小时不间断值班」→ 建 ServiceHours 关联 Authority：
  ```jsonc
  { "ref": "sh-24h", "type": "ServiceHours",
    "featureName": { "eng": "24-Hour Watch", "zho": "24小时值班" },
    "attributes": { "scheduleByDayOfWeek": {
        "categoryOfSchedule": "normal operation",
        "timeIntervalsByDayOfWeek": { "dayOfWeek": ["Sunday", "Saturday"],
          "dayOfWeekIsRange": true,
          "timeOfDayStart": "00:00:00", "timeOfDayEnd": "24:00:00" } } } }
  ```
  注意：`scheduleByDayOfWeek` 作为**复合属性的子属性**时（如 `telecommunications/scheduleByDayOfWeek`），
  仅表达该条联系方式的运营时间。

### 5.3 船舶报告制（指南 5.7）

**SRSA**
- 「报告范围内适用的船舶」→ SRSA 关联 APPLIC，关联关系 `required`
- `requirementsForMaintenanceOfListeningWatch`：
  - 已知 → 英文 + 中文，如 `["maintain a continuous listening watch on VHF08", "在VHF08频道上保持守听"]`
  - 已知无要求 → `not applicable`
  - 未知 → `unknown` / `not specified`

**ShipReport**
- `noticeTime`：提前报告时间（`noticeTimeHours`）
- 报告格式、内容、方式等其他描述 → 填 `textContent`，不要塞进 `noticeTimeText`
- `imoFormatForReporting`：是否经 IMO 认证
- 「在某报告时机要求向某机构报告」→ ShipReport 用 **`reportTo`** 指向 Authority
  （详细联系方式由 Authority 的 `theContactDetails` 获得）；
  「哪些船舶须报告 / 免除报告」用 **`mustBeFiledBy`** 指向 APPLIC，
  **不是** `controlAuthority` / `permission` —— XSD 里 ShipReport 上没有这两个角色
- **同一来源、相同 `categoryOfShipReport` 的报告要求填进同一个 ShipReport**

`categoryOfShipReport` 判别：

| 枚举值 | 报告时机 |
|---|---|
| `sailing plan` | ①启航时/前（含拟进出航道、桥梁通航孔、锚地等特定位置）②进入系统覆盖区域时。**船舶预报告归此类** |
| `final report` | ①抵达目的地时 ②离开系统覆盖区域时 |
| `deviation report` | ①实际位置显著偏离预设航线 ②主动更改已报备计划 ③船长研判需报告 |
| `position report` | 按规定时间间隔/时机进行的船位报告，**较少使用** |

> 常见错误（指南 6.4）：船舶经过特定位置向 VTS 报告动态 → `sailing plan`，**不是** `position report`。

**RadioCallingInPoint**
- 作为船舶报告系统/VTS 报告系统的构成部分时 → **聚合关联**到 SRSA（`componentOf`）
  这样可通过 SRSA 间接获得主管机构、联系机构、报告要求
- SRSA 与 RadioCallingInPoint **无继承关系**，因此
  「报告区内的适用船舶」和「经过报告点/线要求报告的船舶」**两者都要各自关联 APPLIC**
- 条文要求通过报告线时须报告 → RadioCallingInPoint **必须**关联要求报告的 APPLIC
- 通过报告线**免除**报告的船舶 → `ShipReport` 关联 APPLIC，关联类型 `not required`；
  该船舶类型只能用 text 表达属性时，也可把免除内容填进 `ShipReport/textContent`
- 报告线位置能用的**所有** VHF 频道都填进 `communicationChannel`，格式 `VHF08` 或 `VHF CH08`

### 5.4 VTS（指南 5.8）

- `categoryOfVesselTrafficService`（多重枚举）：
  `Information Service` / `Traffic Organisation Service` / `Navigational Assistance Service`
  （「支持联合行动」属交通组织服务）
- `textContent` 表达 VTS 范围内需遵守的航行规则 —— **无需**建「一对一」的信息要素
- `requirementsForMaintenanceOfListeningWatch` 规则同 SRSA
- 文件明确描述为**分区**、或不同区域值守频道不同 → 分区与总区**都建**，关联关系都要完整
- 范围相同的 VTSA 与 SRSA：前者报告规定来自交通管理规定/VTS 指南，
  后者来自船舶报告制文件 → **各自关联对应来源的 ShipReport**

### 5.5 引航（指南 5.9）

- `PilotageDistrict`：需遵守引航规定的区域
- `PilotBoardingPlace`：引航登离轮位置；有专用通信频道时用 `communicationChannel` 编码；
  **一般与 ENC 一致，S-127 中不予表达**
- `PilotService`：引航服务覆盖范围 + 引航机构资质/服务类型
- 引航报告一般建 `ShipReport`（类型 `any other report`）关联 VTSA
  （引航相关地理要素与 ShipReport 无关联）
- 引航、拖轮等服务的联系方式在航线规划或入港前预定，
  因此这些 `ContactDetails` 应与 **VTS 服务区域**地理要素关联
- 「特殊要求」填进 `PilotBoardingPlace/destination`（表示以相关港口为靠/离泊点的船舶在此登离轮）
- 关联：`PilotService` ↔ `PilotBoardingPlace` / `PilotageDistrict`

### 5.6 富余水深（指南 5.10）

`underkeelAllowance` 子属性：

| 子属性 | 含义 |
|---|---|
| `underkeelAllowanceFixed` | 固定富余水深值，单位米，精度 0.1 |
| `underkeelAllowanceVariableBeamBased` | 基于**船宽**的百分比 |
| `underkeelAllowanceVariableDraughtBased` | 基于**吃水**的百分比 |
| `operation` | 多个参数取最大/最小值，如 `largest value` |

`waterLevelTrend` 是 **UCAA 的直接属性**，不在 `underkeelAllowance` 里面
（水位变化趋势对富余水深的影响，`decreasing` 表示水位下降、要求更大富余水深）。

**不同条件下的富余水深要求必须建多个 UCAA 分别表达，即使几何范围完全相同。**

案例：
> 主航道内船舶富余水深不得小于 1.7 米。主航道内 25 万吨级及以上船舶航速大于等于 8 节时，
> 富余水深不得小于船舶吃水的 13%。

- UCAA-1：`underkeelAllowanceFixed = 1.7`
- UCAA-2：`underkeelAllowanceFixed = 1.7` + `underkeelAllowanceVariableDraughtBased = 13`
  + `operation = largest value`，
  `textContent/information/text = ["Vessel speed not below 8 knots", "船舶航速大于等于8节"]`，
  关联 APPLIC「25万吨级及以上船舶」（`required`）
  —— 该 APPLIC 的参数只能用 `information/text` 表达（「吨级」非具体参数）

另一案例：
> 保留不小于船舶吃水 10% 的富余水深。载运危险货物的另加 0.1 米，航速超过 12 节的另加 0.1 米。

→ 建 3 个 UCAA：
1. `VariableDraughtBased = 10`
2. `VariableDraughtBased = 10` + `Fixed = 0.1`，关联 APPLIC「载运危险货物船舶」（`required`）
3. `VariableDraughtBased = 10` + `Fixed = 0.2`，关联 APPLIC「航速超12节的载运危险货物船舶」（`required`）

**UCMA**：`dynamicResource = 2`（强制外部动态信息）或 `3`（可选）时，
外部数据源**必须**通过关联 ContactDetails 的属性编码。

### 5.7 桥梁（指南 5.13）

> 「船舶通过韩江大桥时富余净空高度应当不少于 0.3 米。」

- 桥区范围建 `RestrictedAreaNavigational`（或桥区水域建 `WaterwayArea`），条文填 `textContent`
- 桥区范围**优先按来源文件**创建；文件未提及时，去相关机构官网查
  「海上交通安全管理条例」「桥区水域管理规定」「桥区水域通告」等关键词，按相关条款勾绘
- 桥梁净空高信息填进桥区水域要素的 `textContent`，
  并**同步更新**到智慧航保数字服务系统的通航要素

## 六、子元素顺序（脚本已内置，无需手工排序）

顺序完全由 `scripts/s127_schema.py`（XSD 生成）决定，`build_gml.py` 自动套用。
XSD 的 `xs:sequence` 形状是：

```
s100:featureObjectIdentifier（仅地理要素）
→ fixedDateRange → periodicDateRange → featureName（可多个）→ sourceIndication
→ textContent → 【关联元素】 → 【该要素类专有属性】 → geometry（仅地理要素）
```

注意**关联元素在专有属性之前** —— 因为它们定义在继承链上层
（FeatureType → OrganisationContactArea → SupervisedArea → ReportableServiceArea），
XML Schema 规定基类 sequence 必须排在派生 sequence 之前。

而 13 个已入库的生产数据集（CARIS 导出）是**专有属性在前、关联在后**，
16 个要素类中 8 个与 XSD 冲突。因此构建器提供两种版式：

| 模式 | 用法 | 说明 |
|---|---|---|
| `--order xsd`（默认） | 新数据集 | 严格符合 S127.xsd |
| `--order caris` | 与历史归档比对/续编 | 复现既有 GML 版式（实测与生产数据逐元素一致） |

复合类型也有两处差异，同样受 `--order` 控制：
`fixedDateRange`（XSD `dateStart→dateEnd`，CARIS `dateEnd→dateStart`）、
`sourceIndication`（`featureName` 的位置）。其余 18 个复合类型两边一致。

详细的取舍理由见 `06-GML结构与几何.md` §顺序之争。

> 写了 XSD 里不存在的属性名，`validate_featureset.py` 直接判 ERROR 并提示最接近的正确名
> （例如 `radioCommunications` → `radiocommunications`）。
