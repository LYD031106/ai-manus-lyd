# 关联关系

对应指南 5.5、5.6 节，并以 `schemas/S127.xsd` 校准。
核心原则：**关联非必须，只在对用户有用时才连，避免冗余。**

> 指南 5.3 说「所有地理要素必须关联唯一 Authority」，但 XSD 里
> **只有 11 个要素类有 `controlAuthority`**。其余要素类只能间接获得主管机构 ——
> 见 `02-要素字典.md` §二的说明。校验器按要素类分别提示，不会强求做不到的事。

---

## 一、关联角色表（XSD）

要素清单里 `associations[].role` 的取值。`build_gml.py` 据此生成
`xlink:arcrole="http://www.iho.net/S-127/roles/<role>"` 与 `xlink:title`。
**某个角色能挂在哪个要素类上由 XSD 决定**（`02-要素字典.md` §二有完整表），
写错位置校验器直接判 ERROR。

| role | 关联类（xlink:title） | 挂在 | 指向 |
|---|---|---|---|
| `permission` | PermissionType | 地理要素 | Applicability |
| `vslLocation` | PermissionType | Applicability | Applicability |
| `isApplicableTo` | InclusionType | Regulations / Restrictions / Recommendations / NauticalInformation | Applicability |
| `theApplicableRxN` | InclusionType | Applicability | 规则类信息要素 |
| `theRxN` | AssociatedRxN | 地理要素 | Regulations / Restrictions / Recommendations / NauticalInformation |
| `theContactDetails` | SrvContact | 部分地理要素、Authority | ContactDetails |
| `controlAuthority` | SrvControl | 11 个要素类（见 02 §二） | Authority |
| `theOrganisation` | SrvControl | 规则类信息要素 | Authority |
| `theAuthority` | SrvControl | ContactDetails | Authority |
| `reptForTrafficServ` | TrafficServRept | VTSA / SRSA / LPS / PlaceOfRefuge / UCMA / PilotService | ShipReport |
| `theShipReport` | TrafficServRept | Authority、Applicability | ShipReport |
| `reportTo` | TrafficServRept | **ShipReport** | Authority |
| `mustBeFiledBy` | TrafficServRept | **ShipReport** | Applicability |
| `consistsOf` | TrafficControlServiceAggregation | VTSA / SRSA / LPS / PilotageDistrict | RadioCallingInPoint / 信号站 / RadarRange / PilotBoardingPlace |
| `componentOf` | TrafficControlServiceAggregation | RadioCallingInPoint / PilotBoardingPlace | VTSA / SRSA / LPS / PilotageDistrict |
| `theServiceHours` | SrvHours | Authority、PilotService | ServiceHours |
| `serviceProvider` | PilotServiceAssociation | PilotBoardingPlace / PilotageDistrict | PilotService |
| `serviceArea` | PilotServiceAssociation | PilotService | PilotageDistrict / PilotBoardingPlace |
| `providesInformation` | InformationAssociation | 几乎所有要素 | 信息要素 |

> `consistsOf` 与 `componentOf` 互为反向：只写一侧，`build_gml.py` 自动补齐对端。

**两个容易搞错的地方**：
- `ShipReport` 上**没有** `controlAuthority` 和 `permission`。
  「向某机构报告」用 `reportTo`；「哪些船舶须报告」用 `mustBeFiledBy`。
- `RadioCallingInPoint`、`RouteingMeasure`、`UCAA`、`ConcentrationOfShippingHazardArea`
  上**没有** `controlAuthority`，也没有 `theContactDetails`（报告线除外亦无）。
  联系机构信息通过 `componentOf` 聚合到 VTSA/SRSA 后间接获得。

## 三、Permission Type 许可类型

指定**船舶类别与要素的关系** —— 是否允许/禁止进入某区域，是否需要/建议使用某服务。

| 取值 | 含义 | 用例 |
|---|---|---|
| `required` | 必须的 | `categoryOfDangerousOrHazardousCargo = Class 3` 的 APPLIC 关联 RadioCallingInPoint → 此类船舶经过报告线时**必须**报告 |
| `not required` | 不要求 | `restriction = speed restricted` 的限制区关联 APPLIC → 此类船舶**可不遵守**区域内限速 |
| `permitted` | 允许 | 「300总吨以下自愿加入本报告制的船舶」→ APPLIC 关联 SRSA |
| `prohibited` | 禁止 | WaterwayArea 关联 APPLIC → 此类船舶**禁止进入**该水道 |
| `recommended` | 推荐 | 渔船推荐航路 RouteingMeasure 关联 APPLIC「渔船」 |
| `not recommended` | 不推荐 | 沿海公共航路 RouteingMeasure 关联 APPLIC「渔船」 |

更多用例：
- `UnderkeelClearanceAllowanceArea` 关联 APPLIC `required` → 此类船舶在区域内**必须**遵守富余水深要求
- `restriction = entry prohibited` 的 `RestrictedAreaNavigational` 关联 APPLIC `required` → 此类船舶**不得进入**
- 船舶报告制适用的船舶类型 → `required`

## 四、Inclusion Type 包含类型

描述**船舶类别与特定法规/建议的关系**：
`included` = APPLIC 需遵守关联规则；`excluded` = APPLIC 不受该规则约束。

案例：
> 符合下列情形之一的船舶或船队，应经过海事管理机构安全条件核查后方可进出深圳港口：
> （一）载重吨大于100000吨级，**拟使用**铜鼓航道的船舶；
> （二）拖带长度200米及以上或者拖带宽度40米及以上，**拟进入**深圳水域的拖带船队……

「拟」进入/计划使用，说明船舶应在**抵达前**获得该规定才能保障合规航行。
→ 建 `Regulations` 关联到本条文适用的 `RestrictedAreaRegulatory`（使船舶进入监管范围、
抵达航道前就能获得该规定），相关 APPLIC 与规则关联，类型 `included`。

## 五、关联类型怎么进 GML

### 现状：生产数据里没有类型值

13 个已入库数据集的关联元素只有 `xlink:href` + `arcrole` + `title`，**不带类型**：

```xml
<permission xlink:href="#i1" xlink:arcrole="http://www.iho.net/S-127/roles/permission"
            xlink:title="PermissionType"/>
```

CARIS S-57 Composer **无法选择**关联关系类型（指南 3.3.2(4)），所以生产流程是
导入系统后人工补选。

### 但 schema 支持：PermissionType / InclusionType 是一等对象

S127.xsd 把这两个关联类定义成了可实例化的**信息对象**（继承 `InformationTypeType`）：

```xml
<PermissionType gml:id="i9">
  <categoryOfRelationship code="5">required</categoryOfRelationship>   <!-- 必填 1..1 -->
  <permission xlink:href="#i6" .../>                                   <!-- 指向 APPLIC，1..N -->
</PermissionType>
```

要素侧的 `permission` 元素这时指向**这个对象**（`#i9`）而不是直接指向 APPLIC，
类型值就随 GML 一起走了。`InclusionType` 同理，属性名是 `membership`。

取值来自 XSD 枚举，不要自己编：

| categoryOfRelationship | code | membership | code |
|---|---|---|---|
| `prohibited` | 1 | `included` | 1 |
| `not recommended` | 2 | `excluded` | 2 |
| `permitted` | 3 | | |
| `recommended` | 4 | | |
| `required` | 5 | | |
| `not required` | 6 | | |

### 两种做法，怎么选

```bash
# 默认：与现有生产数据一致，类型进补录清单
python scripts/build_gml.py fs.json -o out.gml --assoc-csv 关联补录清单.csv

# 可选：类型写进 GML（符合 schema，但生产系统未验证过）
python scripts/build_gml.py fs.json -o out.gml --assoc-objects --assoc-csv 关联清单.csv
```

| | 默认（扁平引用） | `--assoc-objects` |
|---|---|---|
| 符合 S127.xsd | 是 | 是 |
| 与 13 个已入库数据集一致 | **是** | 否（生产里没人这么做过） |
| 类型值随 GML 传递 | 否，需系统内补录 | **是** |
| 风险 | 补录漏项 | 导入器可能不认识这些对象，**先拿小样试** |

**建议**：先按默认出，导入验证通过后，若想省掉补录工序，再拿一个小数据集试
`--assoc-objects`，确认系统能正确解析后再推广。

无论哪种做法，**要素清单里都要写 `"permission": "required"` / `"inclusion": "included"`**
—— 不写的话补录清单里该格为空，补录时没人知道该选什么，只能回头翻原文。
校验器会对缺类型的关联告警。

## 六、什么时候该省略关联

- 地理要素与其监管 Authority 关联**相同**的 ContactDetails / ShipReport
  → 省略 Authority 与 ContactDetails / ShipReport 的关联
- VTSA 与 ShipReport 关联**相同**的 APPLIC → 省略 ShipReport 的 `mustBeFiledBy`
- 符合「三方关联关系」时（A→B、B→C、A→C 三条边中有一条可由另两条推出），考虑省略冗余边

## 七、什么时候不能省略

- 条文要求通过报告线时须进行船舶报告 → `RadioCallingInPoint` **必须**关联要求报告的 APPLIC
- SRSA 与 RadioCallingInPoint 之间**无继承关系**，
  「报告区内适用船舶」与「经过报告点/线要求报告的船舶」**各自都要**关联 APPLIC
- 分区与总区（VTS 分区/总区）**两者**与信息要素的关联都要求完整

## 八、常见错误：不该用地理要素关联 APPLIC 的场合（指南 6.3）

> 以下船舶之间可利用长江口深水航道两侧边坡100米水域实施交会：
> （一）邮轮与集装箱船；（二）邮轮与邮轮；……

❌ 错误做法：边坡地理要素关联各类船舶 APPLIC。

地理要素与 APPLIC 的关联表达的是「**关联船舶进入该区域的合法程度**」
（强制/不强制、推荐/不推荐、禁止/允许），表达不了「A 类与 B 类之间可交会」。

✅ 正确做法：把条文转为**规则信息要素**，关联各类船舶 APPLIC，类型 `included`。
