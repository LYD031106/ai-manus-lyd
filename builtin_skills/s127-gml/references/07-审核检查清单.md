# 审核检查清单

交付前逐条走一遍。前两节（不表达清单、已知返工点）是**编码前**就该看的。

## 一、不表达清单（指南 3.2、6.2）

以下内容**不转换为 S-127**。判断错了就是白做，而且会污染数据集。

| # | 内容 | 依据 |
|---|---|---|
| 1 | 海上从业者应掌握的**常规性/常识性内容** | 指南 3.2(4)：着重表达直接影响船舶合规航行的信息 |
| 2 | 「禁止船舶在水下管线两侧保护水域范围内锚泊或拖锚航行」等《海底电缆管道保护规定》相关条文 | 指南 6.2(1)，视作从业者常识 |
| 3 | **海上作业申报**规定 | 指南 6.2(2)，不属于 S-127 表达域（与船舶航行/通航规则无关） |
| 4 | 海上航行、**入港申请**等申报的规则条文 | 指南 6.2(3)，行为主体是船公司/代理而非船舶 |
| 5 | 由指挥中心/VTS 基于观测研判、通过 VHF 通知执行的**临时交通管制**条件 | 指南 6.2(4)，属交通管理要求而非船舶应遵守的航规 |
| 6 | 无线电、雷达等**通信设施的覆盖范围** | 指南第 2 章 |
| 7 | ENC 已表达同等内容的部分 | 指南 3.2(2) |
| 8 | 被新文件完全取代的旧文件内容 | 指南 3.2(1) |
| 9 | 桥区水域范围调整、**代表船型**变化等范围元数据（「桥区水域范围根据航道等级调整、代表船型变化…动态调整并公布」） | 「代表船型」不属于 S-127 表达范围；范围管理条款不作文本属性提取 |

### 第 3 条的细分（重要）

> 在VTS区域内从事水上过驳作业，应在过驳锚地进行，经核查安全条件后方可作业。
> 卸驳船应提前24小时向台州VTS报告。

- 第一句（作业要求）→ **不表达**
- 第二句（报告要求）→ **要表达**：`ShipReport`（`any other report`）+
  `noticeTime = 24 小时` + 关联报告对象 ContactDetails（台州VTS中心）

### 第 5 条的细分（重要）

> 遇下列情况实施单向通航：1.视程小于3000米；2.风力大于等于7级；……7.船长、引航员申请时

整段**不表达**。但同一条文里若有**无条件**的管制（如「259号灯浮标以西实施单向通航」），
那一句**要表达** —— 建航行限制区，条文填 `textContent`。
参见 `05-专题配方.md` §3「管制类条文」。

### 反向：容易误判为「不表达」的内容（指南 7.7）

以下是**地域性新增要求**，国际公约与国内上位法都没规定，因此**要表达**
（优先用结构化属性/枚举，其次填进地理要素或信息要素的文本属性）：
- 从事捕鱼的船舶应避免在通航分道内捕捞
- 不得在警戒区、通航分道及其端部附近水域锚泊 → `restriction = anchoring prohibited`
- 追越时应征得被追越船同意并保持足够横距

## 二、已知返工点

从真实审核记录（`gml校对` / `gml审核` 工作表的「修改意见」列）归纳：

| 返工点 | 正确做法 |
|---|---|
| 要素名称过长 | 简化，如 `Dadeng Bridge-Rail Transit Line 4 Bridge Area Waters`（不要把工程全称写进去） |
| 给 `ShipReport` 挂 `controlAuthority` / `permission` | XSD 里没有这两个角色；用 `reportTo` / `mustBeFiledBy` |
| 给 `RouteingMeasure`、`UCAA`、`ConcentrationOfShippingHazardArea` 挂 `controlAuthority` | XSD 里没有；靠 `theRxN`→Regulations→`theOrganisation` 或系统内关联 |
| 属性名写成 `radioCommunications` | XSD 里是小写 c：`radiocommunications` |
| 英文名与系统内既有要素不一致 | 与系统保持一致；同一实体不要出现两种英译 |
| `source` 英译与文号不对应 | `Fujian Navigational Notice` 对应「闽航通」，逐字核对文号 |
| 桥区范围画错 | 按来源文件；文件未给则依据《海上交通安全管理条例》相应条款划定，并在记录表注明依据 |
| 遗漏系统内同名要素的净高信息 | 补录，并删除系统内重复的旧要素 |
| `text` 里带了条款序号 | 去掉，序号只进记录表 |
| 中英文不成对 | `featureName`、`information` 必须成对 |
| 可复用要素填了来源 | Authority / ContactDetails / ServiceHours / APPLIC 不填 `sourceIndication` |
| 报告类型选成 `position report` | 经过特定位置报告动态属 `sailing plan` |
| 富余水深只建一个要素 | 不同条件必须分别建 UCAA |
| 沿海公共航路漏编两个属性 | 二审后补「所属海区」「航道类型」 |
| 禁止锚泊只写进 textContent 而未用 `restriction` | 「不得锚泊」→ `RestrictedAreaNavigational` + `restriction = anchoring prohibited`（`RestrictedAreaRegulatory` 无此值） |
| 「不得锚泊」带「除…外」例外被判成 `anchoring restricted` | 凡「不得/禁止锚泊」→ `anchoring prohibited`；「除…外」例外用 ShipReport / textContent 另行表达，不改 `restriction` 值 |

## 三、交付前自检

### A. 机器可查（跑脚本）

回归自检（改过脚本后跑一次，确认没把保真度弄坏）：

```bash
python scripts/roundtrip_check.py '示例/**/*.gml'    # 非预期差异应为 0
```


```bash
python scripts/validate_featureset.py featureset.json     # ERROR 必须为 0
python scripts/build_gml.py featureset.json -o out.gml --assoc-csv 关联补录清单.csv
python -c "import xml.etree.ElementTree as ET; ET.parse('out.gml'); print('well-formed OK')"
```

**ERROR（违反 `schemas/S127.xsd`，必须修）**：要素类不存在；该要素类没有这个子元素
（会提示最接近的正确名，如 `radioCommunications` → `radiocommunications`）；
缺少 `minOccurs>=1` 的必填项；超出 `maxOccurs`；枚举 label 不在 XSD 列表；
几何种类与 XSD 几何类型不符（如给 `GM_Surface` 要素塞了线）；
关联目标不存在，或 `permission`/`controlAuthority` 等指向了错误的要素类；
坐标越界；数据集命名违规；日期格式错或起止颠倒；单段 `text` 超 300 字符。

**WARN（指南约定或需人工确认）**：中英未成对；`displayName` 约定；可复用要素填了来源；
专属要素缺来源；条款序号残留；命中不表达清单关键词；经纬度疑似写反；
`text` 总长超 300；未关联 Authority（且该要素类有 `controlAuthority`）；
许可/包含类型未指定；APPLIC 的 `logicalConnectives` 与条件数不匹配；
Regulations/Restrictions 与发文层级不匹配。

> **不会因为「某个可选属性没填」而报错。** XSD 里 `minOccurs=0` 的元素一律不强制 ——
> 原文有就填，没有就不填。要素类的必填项清单见 `02-要素字典.md` §二。

## 四、生产数据里已发现的真实缺陷

用本技能的校验器扫 13 个已入库数据集，命中 **89 处** ERROR。分类如下 ——
新做数据时避开这些坑，同时说明「已入库」不等于「合规」：

| 类型 | 处数 | 说明 |
|---|---|---|
| 单段 `text` 超 300 字符 | 63 | 最长 386 字符。S-127 规定上限 300，导入系统可能被截断 |
| 数据集命名违规 | 14 | 含空格/短横、超 17 字符、缺 `127CN00` 前缀。6/13 个文件的 `datasetTitle` 不合规 |
| `controlAuthority` 出现 2 次 | 7 | XSD `maxOccurs=1`。同一 VTSA 关联了两个主管机构 |
| `componentOf` 出现 2 次 | 4 | XSD `maxOccurs=1`，但一条报告线确实可能同属 SRSA 与 VTSA —— 这是 XSD 的限制（其注释也承认 NIPWG 未讨论此场景），不是纯粹的数据错误 |
| `language` 填成 `Article 9` | 1 | 明显的录入错误 |

另外发现三处**文件名 / `datasetFileIdentifier` / `datasetTitle` 三方不一致**：

| 文件名 | fileIdentifier | datasetTitle |
|---|---|---|
| `127CN00TJHG000002.gml` | `127CN00TJHG000001DS.gml` | `127CN00TJHG000001DST` |
| `127CN00Wenzhou VTS002.gml` | `127CN00Wenzhou VTS001.gml` | `127CN00Wenzhou VTS001` |
| `127CN00CHENGSHAN JIAO VTS.gml` | `127CN00CHENGSHAN JIAO VTS.gml` | `CHENGSHAN JIAO VTS` |

温州 002 与 001 的标识完全相同 —— 归档时会互相覆盖。校验器现在会对
`datasetTitle ≠ name` 给出 WARN。

珠江口有 5 个 `RouteingMeasure` 写成
`<categoryOfRouteingMeasure code="unknown" xsi:nil="true"/>`。
**这不是缺陷，是 DCEG 2.4 规定的正确做法** ——「必填属性取值未知时，必须写成空（null）值」，
与「整个省略」语义不同（省略只允许用于非必填属性）。要素清单里写
`"categoryOfRouteingMeasure": {"$nil": true}`，构建器会输出上面那种写法。

## 五、记录表

```bash
python scripts/make_record_table.py featureset.json -o S-127要素生产与检查记录表.xlsx
```

生成三个工作表：`文件解析` / `gml校对` / `gml审核`，列结构与生产线现行表式一致。
脚本会自动填要素类型、名称、来源、关联及类型；**条款出处需人工补**
（在要素清单里写 `"clause": "附件1 二（三）"` 可自动带出）。

「修改意见」列留给校对/审核人填写；每轮审核后把意见落实回要素清单 JSON，
重新跑一遍 validate → build，保证 JSON、GML、系统三者一致。
